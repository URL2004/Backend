# 장문 엔진 병목·근본 원인 분석 — 2026-09-29

## 결론

이번 장문에서 확인한 문제는 단순한 네트워크 지연이 아니다. **앞 단계에서 끝내야 할 강한 의미 심사가 마지막에 처음 실행되고, 한 요청에 전체 문맥 검사·관계 질문·과거 지적 재판정이 몰리면서 추론/응답 한도를 소진한다.** 별도로 CPU 검사기들의 동일 문장 대조 반복도 확인했다.

운영 기준은 c863be8 / gpt-prod-v2.5.89. 후보 v2.5.90의 180초·입력 중복 제거는 로컬 구현되었으나 문제를 해결했다고 판정하지 않았다. 이번 조사 중 운영 변경 없음. 마지막 실호출은 전체 재생성이 아니라 **기존 전체 결과에 대한 최종 심사만** 실행했다.

## 1. 실제 실행에서 확인한 사실

### 180초 허용 후 실제 재심사

같은 저장 결과, 같은 Sol/high, 같은 최대 출력 10,000토큰으로 실행했다. 과거 지적은 저장된 완료 응답에서 재구성한 자료이며, 이전 중단 요청의 완전한 wire 복제라고 주장하지 않는다.

| 항목 | 구간 A | 구간 B |
|---|---:|---:|
| 원문/결과 글자 수 | 4,699 / 4,458 | 3,990 / 3,968 |
| 시작 전 대기·준비 | 1ms | 69ms |
| 명시적 관계 질문 | 10 | 1 |
| 과거 지적 ID | 6 | 15 |
| 추가 과거 질문 | 0 | 10 |

| 출력 토큰(추론 포함) | 10,000 | 6,400 |
| 그중 추론 토큰 | 8,243 | 5,528 |
| 시간 | 약 171초 | 약 108초 |
| 결과 | 응답 잘림 / 검증 미완료 | 의미 심사 통과 |

- 전체는 완료 1/2로 **통과가 아니다**.
- A는 180초 timeout이 아니라 OPENAI_TRUNCATED_OUTPUT이다.
- A의 출력 JSON이 길어서만 생긴 문제는 아니다. 보이는 응답은 4,486자, 다시 쓴 근거 구절은 603자였고 출력 토큰의 82.4%가 추론이었다.
- B는 과거 지적이 더 많았지만 빨리 통과했다. “과거 지적 개수가 주원인”이라는 초기 가설은 이 사례에서 기각했다.
- 수십 ms의 준비·대기가 수분 지연을 설명하지 못한다.
- 제공자 내부 대기와 실제 추론 생성 시간은 비스트리밍 응답만으로 정확히 분리할 수 없다.
- 몇 건의 출력 토큰/경과시간 비율만으로 보편적인 처리속도나 원인별 기여도를 확정하지 않는다.

## 2. 가장 중요한 구조 원인: 강한 심사가 너무 늦게 도착함

코드 근거:
- engine-gpt-prod/index.js: semanticRestorationEvidence, 최종 prior_failed_semantic_confirmation, allowRepair:false
- engine-gpt-prod/judge.js: judgeAndRepair의 confirmation_first 라우팅과 primary pass 처리
- engine-gpt-prod/finalQualityV2.js: 구간 심사와 최종 판정 전용 모드
- engine-gpt-prod/semanticSegmentReceipts.js: 모델/추론 단계, 구간, 이웃 문맥에 묶인 재사용 조건

잘린 A 응답의 앞부분에는 새 지적 4개가 있었다. 이 4개 구간을 이전 응답과 정확히 대조했다.

- 첫 2개 원문·결과 쌍은 호출 12에 있었고, 동일 쌍이 남은 호출 14에서 Luna가 위반 0건으로 반환했다.
- 나머지 2개도 호출 13에 있었고, 동일 쌍이 남은 호출 15에서 Luna가 위반 0건으로 반환했다.
- 해당 쌍을 최종 이전에 Sol이 심사한 기록은 없었다.
- 따라서 이번 4개 지적을 마지막 공백 정리나 2개 국소 복원이 새로 만든 오류라고 설명할 수 없다.
- **첫 강한 심사가 수리 여유가 가장 작은 최종 단계에 몰린다.** 앞 단계에서는 Luna 판정으로 넘어가고, 마지막에 Sol이 새 문제를 발견한다. 최종 판정 뒤에도 제한적인 수리 분기는 있지만, 완결된 판정과 수리·재검증 시간이 남아 있어야 하므로 이번 미완료 응답에는 적용할 수 없었다.

4개 지적 모두를 확정 오류로 집계하지 않았다. 미완성 응답의 중간 목록이며 게임 진행 방식의 과거형 서술 등은 전체 문맥에 따라 오탐일 수 있다. 반면 행동을 만드는 것에서 생각하는 것으로 약화하거나 기대와의 비교를 생략한 부분은 실제 의미 차이 후보다. 완결된 심사와 직접 문맥 대조가 필요하다.

## 3. 한 요청의 검수 부담을 제어하지 못함

코드 근거:
- judge.js semanticJudge: 전체 의미 감사 + operatorReviews + obligationReviews
- semanticReviewEnvelope.js: confirming이면 10,000토큰으로 고정
- semanticAuditSchedule.js planVerdictPairs: 최종 구간을 최대 6,000자 두 창으로 재편성
- semanticOperatorReview.js targets: includeAllCandidates로 전체 후보 사용

글자 수와 동시성은 제한하지만, **문맥 난도·검토 질문·새 오류 탐색에 필요한 추론량**은 상한 안에 들어오는지 확인하지 않는다. 대기열을 줄이려고 세 구간을 두 창으로 합치면 각 요청이 더 무거워질 수 있다.

단, 이번 한 번의 A/B 결과로 관계 질문 10개가 추론 8,243개의 단독 원인이라고 확정할 수 없다. 본문 길이, 새 문제 발견, 규칙 수가 함께 달랐다. 단순히 3구간으로 되돌리면 동시성 2에서 마지막 구간이 기다리므로 그것도 검증 전 해결책이 아니다.

## 4. 관계 후보의 반복·중복

실제 저장 요청을 대조했다.

- A의 질문 10개 모두 앞선 Luna 호출에서 동일한 원문–결과 쌍으로 두 번씩 preserved를 받았다.
- 그중 9개는 확신/가능성 계열이며 일반 담화 신호 목록에도 동일 구절로 실려 있었다.
- 10개 모두 원문 구절이 서로 달랐다. “같은 원문 문장의 질문을 합치기”는 이 사례에 효과가 없다.
- A에는 이전 Sol 답이 없었다. “Sol 판정 재사용”만 구현해도 이 A가 해결된다는 제안은 기각했다.
- B의 질문 1개는 앞선 Sol 답도 있었지만, 현재 구간·주변 문맥·검토 계약 전체가 같다는 증명이 별도로 필요하다.

후보 규칙은 가능성/확신 표지의 차이를 넓게 잡는다. 실제로 일반 회고나 의견의 의역도 들어온다. 그렇다고 과거형 “수 있었다→했다”를 전부 면제하면, “할 수 있었지만 하지 않았다→했다” 같은 실제 오류를 놓친다. 후보 삭제로 통과율을 올리는 수정은 하지 않는다.

과거 지적은 sourceSpan·type·relation 기준으로 누적된다. 이후 해결됐다고 모든 자료를 버릴 수는 없지만, 현재 문맥까지 묶인 강한 판정의 보존·유효성 검사가 없으면 다시 물어보는 비용이 커진다.

## 5. CPU 병목: 같은 문장 대조를 반복

최종 심사 준비만 20회 무료 재생한 결과:
- 중앙값 151ms, 표본 p95 203ms, 최대 290ms
- 로컬 이벤트 루프 최대 지연 약 306ms
- 같은 relationAudit를 일반 후보 생성과 명시적 관계 질문 생성에서 다시 실행함

추가 전체 엔진 오프라인 프로파일은 저장된 응답만 사용하고 모르는 요청은 실패시켰다. 일부 첫 생성·수정은 일치했지만 시간 기반 분기가 달라졌으므로 **운영 전체 실행의 정확한 재생이나 당시 24.3초의 함수별 증명은 아니다**.

이 프로파일에서 Korean refinement, fingerprint, depth, candidate integrity가 문장 정렬을 반복 호출했으며, CPU 샘플의 주요 hotspot은 engine/koreanText.js의 levenshteinDistance였다.

동일한 실제 원문·결과로 한국어 검사·지문 검사·편집률 계산을 묶은 별도 무료 실험:
- 편집거리 요청 8,645번 중 동일한 인자 쌍 4,935번(57.1%)이 재등장.
- 요청 안에서만 정확한 인자 쌍의 계산값을 재사용하니 실제 계산 3,710번으로 감소.
- 검사 반환값 전체 deep-equality 확인.
- ABBA 순서 시간: 미사용 559/416ms, 사용 411/356ms.
- 3,710개 키, 약 438,522문자. 메모리 상한·요청 간 격리·취소·동시성 검증이 필요.
- JIT/기기 영향이 있으므로 운영 속도 개선률로 발표하지 않는다.
- 실험은 비공개 로컬 래퍼이며 운영 코드에 적용하지 않았다.

기존 textAnalysisCache는 주로 문장/구문 경계 결과를 저장한다. 내용어·정규화·정렬 후보·편집거리의 모든 반복까지 해결하지 않는다.

## 6. 이미 구현한 것과 아직 하지 않은 것

구현한 후보:
1. 원문·결과·지적 ID·질문을 유지하는 최종 입력 중복 제거. 역변환이 원래 JSON과 다르면 기존 자료로 폴백.
2. 구간별 대기·시간·완료·오류·토큰 진단. 최대 32개 행, 초과 집계, 원문 없음.
3. 사용자 승인에 따른 6,000자 초과 장문 최종 상한 180초. 짧은 글 120초, 전체 작업 시간은 초과하지 않음.
4. 추가 60초를 후속 선택적 수리의 새 기회로 사용하지 않도록 후속 수리·재검증은 기존 120초 창을 유지.

중복 제거의 전체 요청 글자 수 감소는 3.6~4.1%였다. 유효한 정리이지만 근본 해결로 부르지 않는다.

아직 구현/실호출 검증하지 않은 근본 수정:
1. 최종에서 필수가 될 강한 판정을 수리 가능한 단계로 옮기는 단계 설계.
2. 마지막 본문 변경까지 정착시킨 뒤, 동일한 구간·문맥·검사 항목·모델 등급에 묶인 판정 재사용.
3. 글자 수만이 아니라 실측 검수 부담을 고려하는 요청 분배.
4. 요청 내부의 정확한 계산 재사용과 긴 동기 계산의 분할.
5. 마지막 신규 지적 4개의 완결된 판정·필요한 국소 수정.
6. 최신 통합본의 장문 전체 재생성.

## 7. 다음 수정의 합격 기준

- 강한 심사를 단순 추가하지 않고 기존 최종 호출의 책임과 위치를 재배치한다. 실제 총 호출·비용이 늘었는지 확인한다.
- 수리 가능 단계에서 확정된 신규 오류를 고치고, 마지막에는 검증된 후보의 문자열·구조·문맥 유효성을 확인한다.
- 다른 구간·다른 이웃 문맥·낮은 등급의 판정을 재사용하지 않는다.
- 후보 질문은 정상 회고/공유 양태와 실제 확신 강화·부정·비현실 가능성을 구분하는 대조군으로 검증한다.
- 잘린 JSON의 앞부분을 완성된 통과 판정으로 채택하지 않는다.
- 편집거리/정렬 최적화는 전후 결과 완전 동일성과 요청 간 격리를 먼저 입증한다.
- 세 문서 동시 실행, 취소, 20문단/120문장 및 실제 장문에 대한 계산 시간과 이벤트 루프 지연을 따로 본다.
- 실제 장문을 처음부터 끝까지 재생성하고 전체 문맥 대조를 마친 뒤 배포 여부를 결정한다.

## 8. 협업 기록 요약

실제 Claude Opus 5.5와 Fable 5.1 구독 CLI 세션을 사용했다. 최초 구현 라운드에서는 각자 담당 파일을 패치·테스트했고, 후속 원인 분석 라운드는 읽기 전용이었다.

- Opus: “대기열보다 요청 하나의 검수 부담을 확인해야 한다.”
- Fable: “과거 지적 개수가 더 많은 쪽이 먼저 통과했다. 지적 수가 원인이라는 초기 가설을 철회한다.”
- Root 실측: A 질문 10개는 Luna 답만 있었고, 새 지적 4개 문장도 앞 단계에 이미 존재했다.
- Fable의 제안: 첫 강한 심사가 마지막까지 미뤄지는 단계 설계를 바꿔야 한다. Root 확인 결과 후속 수리 분기 자체는 있으므로, 정확한 문제는 수리가 절대 불가능한 것이 아니라 완결된 판정과 재검증 여유를 확보하기 어렵다는 것이다.
- Root 결정: 시간/토큰 한도만 추가하지 않고, 강한 심사 시점·구간 고정·계산 재사용을 우선 수정 대상으로 한다.

일부 발언의 “입력 크기가 원인에서 제외된다”는 단정은 채택하지 않았다. 입력·본문 난도·질문 수가 통제되지 않은 소표본이므로 단독 원인을 분리했다고 볼 수 없다. 위 인용은 전달된 기술 결론의 요약이며 모델 내부 추론 기록이 아니다.
