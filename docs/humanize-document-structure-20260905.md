# 휴머나이징 문서 보존 보완과 구조 개선 설계

구현 버전: `gpt-prod-v2.5.44`, 입력 사전 검사 버전: `18`.
이번 구현은 추출 문서의 손상 복원과 기존 보존 기능 보완이다. 목차를 바꾸거나 문단을 다른 절로 옮기는 구조 개선 모드는 아래 설계 제안이며, 이번 버전에 활성화하지 않는다.

## 이번 구현

| 문제 | 원인 | 수정과 적용 경계 |
| --- | --- | --- |
| 페이지 번호가 목록으로 잠기고 페이지 본문에 제목이 섞임 | 페이지 추출 텍스트를 일반 문장/목록으로 바로 분류 | `extractedPageLayout.js`에서 3개 이상의 연속 페이지 번호와 보고서·표지·페이지별 제목 근거를 함께 확인한 뒤 번호를 분리하고 기존 제목/목록 경계를 복원 |
| 페이지 경계에서 한 단어가 둘로 끊김 | 물리 페이지 경계를 의미 문단 경계로 처리 | 같은 문서에 완성된 어절이 실제 존재할 때만 연결. 불확실한 경계는 유지하고 확인 알림 |
| 정상 단어가 합쳐질 위험 | PDF 공백 두 칸을 단어 분절이라고 일괄 해석 | 반복 공백 정리와 어절 연결을 분리. 공백 폭만으로 합치지 않으며 직접 인용·표·코드·URL을 보호 |
| 표지 제출 정보와 로마 숫자 참고문헌이 편집 대상이 됨 | 메타데이터/참고문헌 제목 변형 인식 누락 | 짧은 제출 정보 행을 잠그고 `IV. 참고문헌`과 같은 제목을 인식해 참고문헌 전체 보존 |
| 짧은 결론을 두 문장으로 다시 설명함 | 일반 중복 검사의 최소 문장 길이보다 짧음 | 동일한 필요성 주장을 새로 반복한 제한된 패턴을 검사. 원문 지지 문장 1개, 사실/부정/범위 보존 및 기존 최종 무결성 검사 통과 시에만 제거 |
| 원문의 단위·처분 대상이 모호함 | 윤문과 사실 보정의 경계가 흐려질 수 있음 | 용량 단위 및 처분 대상의 특정 모호성 패턴에 확인 알림. 원문 내용을 추정 보충하지 않으며 불확실성을 확정하지 않도록 기존 프롬프트 보완 |
| URL의 `v=2` 같은 매개변수가 수식으로 인식됨 | 수식 정규식이 URL/인라인 코드의 소유 영역을 구분하지 않음 | 수식 보호 전후에 같은 URL/인라인 코드 제외 규칙을 사용해 구조·수식 오탐 방지 |

페이지 복원은 페이지 번호를 제외한 비공백 문자 순서가 원문과 완전히 같아야 적용된다. 번호 순서가 불명확하거나 근거가 부족한 입력은 그대로 둔다. PDF 원본의 서체, 여백, 표 좌표를 복원하는 기능은 아니다.

추가 검사 자체는 모델을 호출하지 않으며 외부 패키지를 추가하지 않는다. 구조 인식이 정확해지면서 편집 청크의 수와 경계가 달라질 수 있으므로 문서 전체 호출 수가 항상 같거나 줄어든다는 뜻은 아니다. 모델/동시성/과금 정책은 변경하지 않는다. 입력 크기별 운영 처리 시간 개선율은 이번 수정만으로 단정할 수 없다. 전문 분야 알림은 출처 검증이나 의료·법률 사실 판정을 대신하지 않는다.

## 운영 검증에서 발견한 실행권 경합 보완

합성 보고서의 운영 실행 전 대기 173초, 실행 25초를 관측했다. 해당 작업 로그에서 Firestore `ABORTED: Too much contention on these documents`가 확인됐고, 실행권 획득은 실행권→작업→탈퇴 문서 순서, 작업 저장은 탈퇴/활동/실행권 문서를 병렬로 읽어 공통 문서 잠금 순서가 일치하지 않았다.

`transformExecution.js`와 `routes/transform.js`의 공유 문서 접근 순서를 탈퇴→활동(해당 처리에서 사용 시)→실행권→작업으로 정렬했다. 실행권 획득 거절, 만료/다른 소유자의 갱신·해제에서는 공유 실행권 문서를 불필요하게 쓰지 않는다. 소유권 검증, 중복 실행 차단, 풀별 동시 실행 상한, 유효한 실행권 갱신은 유지한다.

잠금을 가진 트랜잭션을 동시에 실행하는 회귀 테스트에서 기존 코드의 순환 대기와 불필요한 공유 쓰기를 재현했고 수정 후 통과했다. 일반 직렬 메모리 DB 테스트만으로는 드러나지 않는 문제였다. 운영 시간 변화는 동일 조건의 개별 검증 사례로 보고하며 이를 운영 전체 p95 개선율로 해석하지 않는다. 엔진 문장 변환 버전은 계속 `v2.5.44`이며 이 후속 수정은 실행 조정 계층에 적용한다.

## 검증 범위

- 합성 회귀 사례: 페이지·절 번호 분리, 어절 연결, 비공백 문자 보존, 반복 적용 안정성, 표지/참고문헌 잠금, 일반 번호 목록 오탐 방지, 시·코드·인용·표 보호.
- 중복 검사: 생성된 필요성 반복 제거, 원문부터 두 번 나온 주장·다른 범위·수치·부정 표현 보존, 실제 최종 엔진 검사 통과.
- URL/수식 검사: URL 매개변수와 인라인 코드를 제외하면서 실제 수식은 왕복 복원.
- 프롬프트: 기존 장르별 길이 상한 유지. 이미 존재하는 중복 방지 지침을 중복 추가하지 않음.
- 개인정보 없는 합성 보고서를 운영 모델 설정으로 실행하여 표지·목차 순서·참고문헌 원문 일치 및 `qualityStatus=clean` 확인. 이는 개별 실행 결과이며 모든 문서의 생성 품질을 보장하는 수치가 아니다.
- 원문 첨부, 실제 사용자 식별 정보, 로컬 평가 산출물 및 API 실행기는 저장소에 포함하지 않음.

## 권장 제품 동작

문장 변환 강도와 구조 변경 권한을 분리한다. 기존 요청은 `structureMode=preserve`로 해석한다. `improve`는 사용자가 별도 선택할 때만 사용하며, 과제 양식의 고정 목차/항목을 제약으로 받는다. 계약서, 문항, 표, 시 등 구조 자체가 의미인 문서는 자동 이동 범위에서 제외하거나 전용 정책을 적용한다.

보존 모드에서는 문장 표현과 확인 가능한 추출 손상을 다듬는다. 구조 개선 모드에서는 사용자가 변경안을 확인할 수 있게 목차, 문단 이동, 분리/결합 이유를 제시한다. 결과의 읽기 화면에는 개선된 글과 변경 요약을 보여주며 내부 토큰이나 검사기 용어는 노출하지 않는다.

## 엔진 설계

현재 `structureChunk.js`의 잠금, 절 위치, 경계 토큰과 `humanizeContract.js`의 문단 변경 권한을 확장한다. 현재 보존 계약에 목차 변경 지시를 덧붙이면 모델이 만든 이동을 후단 검사가 손상으로 간주하는 충돌이 발생한다. 구조 변경 계획을 별도의 승인된 기준으로 관리해야 한다.

1. **문서 모델 생성**: 제목/문단/목록/표/직접 인용/참고문헌에 안정적인 `blockId`, 원본 구간, 절 경로, 잠금 이유를 부여한다. 원본, 추출 복원본, 재배치 기준본의 대응을 유지한다. 동일한 문장이 여러 곳에 있어도 문자열 검색 하나로 위치를 결정하지 않는다.
2. **진단과 계획 생성**: 문단 역할, 원인과 대책 연결, 결론에 새로 등장한 논의, 주장 중복, 근거 누락을 진단한다. 모델은 완성 원고 대신 허용된 이동/분리/결합 작업과 이유를 구조화된 데이터로 반환한다. 사실을 추가해야 하는 문제는 작업 목록의 확인 사항으로 남긴다.
3. **서버 계획 검증**: 문서 소유권, 원본 해시, 계획 버전, 존재하는 블록 ID, 이동 대상, 작업 수 상한, 금지 역할, 목차 제약을 검사한다. 순환 배치, 중복 ID, 출처 없는 새 주장과 미승인 제목 변경은 거절한다. 프롬프트 내부의 문서 내용은 명령으로 해석하지 않는다.
4. **결정론 재배치**: 유효한 계획을 코드로 적용해 글의 순서를 확정한다. 원본 내용과 승인된 변경의 대응표를 유지한다. 전체 문서를 재생성해 계획을 적용하지 않는다.
5. **필요한 문단만 윤문**: 이동 때문에 지시어·연결어가 어색해진 문단과 요청된 대상만 기존 휴머나이징 엔진에 전달한다. 해당 단계에서는 새로 확정한 문단 경계를 잠근다. 인용과 그 주장은 함께 이동한다.
6. **최종 검증**: 사실·수치·단위·고유명사·직접 인용은 원본을 기준으로 검사하고, 순서와 경계는 승인된 재배치 기준본을 검사한다. 누락된 주장, 중복 생성, 잘못된 절 참조, 떨어져 나온 인용, 계획 외 변경을 각각 확인한다. 재배치본을 새로운 사실 원본으로 취급하지 않는다.
7. **제한된 복구**: 실패한 편집 블록만 안전한 재배치 기준본으로 돌린다. 계획 자체가 유효하지 않으면 보존 결과와 적용하지 못한 이유를 반환한다. 전체 재작성 재시도를 반복하지 않으며 현재 복구 호출/시간/비용 상한을 재사용한다.

제안 모듈은 `documentStructure.js`, `structurePlan.js`, `structurePlanAudit.js`, `structureExecutor.js`다. 실제 적용 시 기존 역할 분류/사실 검사/복구 예산을 재사용하고 중복 구현하지 않는다. API는 계획 생성과 적용을 구분하되 서버가 발급한 문서 소유권·원본 해시·계획 버전 결합을 검증한다. 클라이언트가 보낸 `approved=true`만으로 신뢰하지 않는다.

## 병목과 운영 검증

계획 단계는 문서당 최대 1회로 시작하고, 본문 전체 재생성 대신 변경 대상만 제한된 동시성으로 처리한다. 반복 검증을 줄이려면 각 단계의 입력과 출력 버전 및 이미 통과한 잠금/사실 검사를 명시적으로 관리한다. 반복된 전체 스캔의 실제 비용을 계측한 후 캐시 여부를 결정한다.

관측 항목은 파싱·계획·윤문·검증별 지연, 글자 수/편집 가능 블록 수, 요청당 모델 호출·토큰·비용, 재시도·복구 비율, 계획 적용률, 보호 블록 손상/오탐, 주장 누락·중복, 결과 오류율이다. 운영 p50/p95는 길이·장르·구조 모드별로 분리한다. 로그에는 본문·인명·학번·인용 전문을 남기지 않는다.

출시 조건은 금지 구조 변경 0건, 보호 사실·인용 손실 0건, 기존 보존 모드 회귀 없음이다. 별도로 사람이 평가한 문단 흐름·논리 연결·자연스러움과 사용자의 변경안 수용률을 본다. 자동 AI 탐지 점수를 글의 품질이나 작성자 판정으로 대체하지 않는다.

순서는 문서 모델/진단 → 변경안 미리보기 → 제한된 보고서 구조 개선 → 검증을 통과한 장르 확대가 적합하다. 양식이 고정된 과제는 해당 양식을 가장 높은 구조 제약으로 유지한다.
