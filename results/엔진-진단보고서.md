# 당근대학생 휴머나이저 엔진 — 진단 보고서

작성: 2026-06-09 / 대상: 카피킬러(CopyKiller) AI생성검사 우회 엔진

---

## 0. 한 줄 요약

엔진은 원본 65~100%의 AI 의심률을 **안정적으로 40~55%대로 낮춘다**(−20~−46%p). 그러나 **40% 아래로는 메모리스(추가 사실 주입 없이)로 내려가지 못한다.** 직접적 이유는 세 가지다:
1. **카피킬러를 정확히 흉내 내는 내부 채점기가 없다**(블랙박스 + 데이터 9개). 그래서 내부 점수에 "세게 최적화"하면 카피킬러와 오히려 멀어진다(Goodhart 법칙 — 공부글 51%→70% 역전이 바로 이것).
2. **순수 추상 글의 "구체 근거 부족" 플래그는 원리상 메모리스로 못 깬다**(FLOOR가 날조를 금지하므로).
3. **런-투-런 노이즈가 ±10~15%p**로 커서, 작은 개선은 노이즈에 묻힌다.

## 2. 엔진 구성 (파이프라인)

입력 원문 → **청크 분할**(chunk.js, 문단 단위) → 각 청크 **휴머나이즈**(prompt.js 시스템프롬프트 + LLM, 실패 시 재시도/폴백) → **mergeChunks** →
→ **judge**(judge.js, 위험신호 트리거 시 닫힌세계 사실검증+repair) →
→ **grounding**(grounding.js, 추상 segment를 원문 구체로 stance-sharpening) →
→ **optimize**(optimizer.js, `OPTIMIZE=1`일 때 — 고위험 segment를 후보 N개 중 riskScore 최저로 교체) →
→ **polish**(polish.js, 구어체 틱·register 혼합·압축 국소 repair) →
→ **antidetect**(antidetect.js, 옵션 — perplexity 교란) →
→ **spacing**(spacing.js, 결정론 띄어쓰기) →
→ **FLOOR 측정/출고 판정**(floor.js — novelty 0·분량·반복·결론 보존 확인, 위반 시 폐기/블록).

**설계 철학**: FLOOR(사실·화자·결론 보존, 날조 금지)가 항상 우회보다 우선. 모든 우회 패스는 FLOOR 재검을 통과해야만 채택되고, 깨지면 직전 버전으로 되돌린다(무해성 보장).

**핵심 측정 지표**:
- `floor.measureNovelty` — 원문에 없는 수치·고유명사·기관 = 날조(0이어야 출고).
- `surfaceguard.measureSegmentRisk.riskScore` — 카피킬러 영역 의심을 예측하는 내부 프록시(0~1). generic·uniformity·impersonal·compression 가중합.
- 카피킬러 % ≈ (의심 영역 수 ÷ 전체 영역 수). **길이 가중**(긴 글일수록 영역 많음).

- 메모리스 바닥 ≈ **40~55%**, 편차 큼.

- 유일하게 명확히 내린 건 **대학 55→46(opt cap12, 가벼운 최적화)**. 세게 하면(cap35) 오히려 악화.

## 4. 지금 더 나아가지 못하는 이유 (핵심)

### 이유 A — 카피킬러를 흉내 내는 "충실한 채점기"가 없다 (가장 근본)
- 내부 riskScore는 자연 변이 글 5개에서 카피킬러와 **순위상관 0.90**으로 검증됐다.
- 그러나 그 채점기를 **최적화 목표로 삼는 순간** 규칙이 깨진다(**Goodhart 법칙**: "측정값이 목표가 되면 더는 좋은 측정값이 아니다"). 옵티마이저는 riskScore가 낮은 지점을 찾는데, 그 지점이 카피킬러에겐 높은 영역일 수 있다.
- **증거**: 공부글에서 cap을 12→35로 올려 더 세게 최적화 → 내부 meanRisk 0.090→**0.065(좋아짐)**인데 카피킬러는 51%→**70%(나빠짐)**. 최적화를 세게 할수록 발산.
- 근본 원인: 카피킬러는 **블랙박스**이고, 우리가 가진 라벨 데이터는 PDF **약 9개뿐**. 진짜 surrogate(대리 모델)를 학습시키기엔 턱없이 부족하다.

### 이유 B — segment 재작성이 내용을 "복제"하는 버그
- 옵티마이저/grounding는 글을 ~350자 segment로 쪼개 일부만 재작성 후 다시 합친다.
- LLM이 한 segment를 고칠 때 **인접 segment의 내용까지 다시 진술**하면, 병합 시 같은 내용이 **두 번** 들어간다.
- **증거**: 공부글 cap35 출력은 **인트로가 통째로 중복**됨("공부라는 말, 누구나 알아요…"가 두 번). cap12(중복 2건)→cap35(중복 3건+인트로)로, 많이 건드릴수록 중복↑.
- 카피킬러의 **"동일 내용의 과도한 반복"** 플래그가 여기서 터진다. 품질도 즉시 망가진다.

### 이유 C — 순수 추상 글의 바닥 (구조적)
- 추상위험 0.9+ 글(경영·공부)은 카피킬러가 **"추상적·일반적 내용 / 구체적 근거 부족 / 무견해"**(중간 강도)를 안정적으로 잡는다.
- 이건 **원문에 구체(수치·사례·1인칭 장면)가 없어서** 생기는 플래그다. 옵티마이저의 anchor 후보도 *없는 구체는 만들 수 없다* — FLOOR가 날조를 금지하기 때문.
- 반례가 증명: 구체가 있는 글(개인정보 41%, IT 중간0개)은 깊은 플래그가 사라진다.
- → **sub-40은 구체 주입(사용자 메모 또는 검증된 evidence-pack)이 있어야만 가능.** 메모리스로는 원리적 한계.

### 이유 D — 런-투-런 노이즈가 크다
- 같은 글·같은 설정도 LLM 재작성이 매번 달라 **±10~15%p** 흔들린다(건강 35·45·47·59 등).
- 작은 개선은 이 노이즈에 묻혀 측정으로 확인이 안 된다. 그래서 "개선인지 노이즈인지" 판별 자체가 어렵다.

## 5. 엔진 문제점 (구체적 결함)

1. **[심각] 옵티마이저 over-optimization** — 내부 프록시에 과적합. cap을 올릴수록 카피킬러와 발산(공부 51→70). 현재 multi-candidate 선택 로직은 "카피킬러를 못 속이는데 속였다고 착각"한다.
2. **[심각] segment 재작성 중복** — 인접 내용 재진술 → 병합 중복. novelty=0(원문 내용이라)·register OK로 게이트를 통과해버려 못 걸러진다.
3. **[중] 압축 측정 미스매치** — 내 compressionRatio는 *문장* 단위(쉼표·추상명사)인데, 카피킬러 "지나친 요약·압축"은 *문단* 단위(한 문단에 논점 과다). 측정기가 카피킬러가 잡는 걸 못 본다.
4. **[중] base 휴머나이즈의 한다체 혼입** — blog 톤이 burstiness용으로 "체언 종결·한다체"를 일부러 섞는데(예: "…법이다"), 카피킬러가 이를 **"간접화법·비인칭"**으로 잡는다. 균일성↔비인칭이 상충.
5. **[중] phrase 예산이 길이 무시** — "거든요" 예산 5가 22K자 긴 글엔 부적합(밀도로 봐야 함).
6. **[경] 측정 비가시성** — engine-test가 polish/optimize/spacing 통계를 출력하지 않아 디버깅이 어렵다.
7. **[경] 비용/시간** — 긴 글 + cap35 multi-candidate = API 12~13분. cap을 올리면 비용·시간 급증.

## 6. 계속 해결되지 않는 부분 (명시)

다음은 **여러 차례 시도했으나 메모리스로는 안 풀린** 것들이다:

- ❌ **순수 추상 글 sub-40** — 경영(64% plateau), 공부(51%). "구체 근거 부족" 플래그는 구체 주입 없이 불가. (FLOOR 원칙상 엔진이 못 지어냄)
- ❌ **"지나친 요약·압축" 플래그** — 문단 단위라 현재 문장 단위 측정기로는 검출·수리 안 됨(건강·공부에서 반복 출현).
- ❌ **"기계적 균일성" 완전 제거** — 옵티마이저가 줄이긴 하나(대학 3→0), 긴 글에선 cap·노이즈로 잔존.
- ❌ **"간접화법·비인칭"** — base의 한다체 혼입이 원인. 옵티마이저 후보만 고쳐선 base가 안 고쳐짐.
- ❌ **% 의 안정적 하락 보장** — 노이즈 ±15%p + 프록시 발산으로, "개선"이 측정에서 역전되는 일이 반복.
- ⚠️ **메모(evidence) 주입** — 메커니즘은 됨(WHO 통계 위빙·judge 통과 확인)이나, 잘못 넣으면(길게·균일하게) 오히려 ↑(건강 45→59). "segment당 1개 짧게"가 원칙인데 아직 그 모드 미완성.

## 7. 보완 방향 (정직한 우선순위)

**즉시 (버그·역효과 제거)**
1. **옵티마이저 cap을 다시 낮춰라(12 이하)** — 세게 최적화가 역효과. 가벼운 최적화가 더 안전(대학 55→46이 cap12).
2. **중복 검출 게이트** — 재작성 전/후 문장 중복(같은 12+자 시퀀스 2회+)을 검출해 중복 유발 후보 폐기. (floor.measureRepetition 확장)
3. **base blog 톤에서 한다체/체언종결 제거** — "해요체 안에서만" 종결 다양화로 비인칭 플래그 차단(균일성은 옵티마이저가 담당).

**중기 (진짜 신호 확보)**
4. **카피킬러 PDF 라벨을 체계적으로 축적** — 매 측정마다 영역별(의심/사유)을 JSON으로 저장. 20~30개 모이면 채점기 가중치를 *실측에 회귀*로 보정(지금은 감으로 정함).
5. **문단 단위 압축 측정기** — distinct 논점/문단 밀도로 "지나친 요약" 검출 → decompress 후보 연결.

**제품 (바닥 돌파)**
6. **evidence-pack 모드(segment당 1개·짧게·해석 1문장)** — 순수 추상 글의 "구체 근거 부족"을 검증된 공개 사실로 보강. 학술 정직성 고지 동반.
7. **입력 등급(A/B/C) 사전 표시** — 추상위험으로 달성 가능 %를 미리 안내(C등급 순수추상은 40%대가 한계임을 명시).

## 8. 결론

- 엔진의 **보존(FLOOR)·1차 휴머나이즈·가벼운 segment 최적화**는 견고하다. 원본 대비 −20~−46%p는 실재하는 성과다.
- 막힌 지점은 **"카피킬러를 정확히 모방하는 신호의 부재"**와 **"순수 추상 글의 구조적 바닥"**, 두 축이다.
- 따라서 다음 한 수는 *더 센 프롬프트/최적화*가 아니라 **(1) 역효과(중복·과최적화·한다체) 제거 → 안정화**, 그리고 **(2) 실측 라벨 축적으로 채점기를 카피킬러에 정렬**이다.
- sub-40을 원하면 **구체(메모/evidence)**가 불가피하다 — 이는 엔진의 한계가 아니라 "없는 사실을 지어내지 않는다"는 원칙의 당연한 귀결이다.
