## 0. 먼저 알아야 할 현실 3가지

1. **운영(prod)은 옛 코드로 돌고 있다.** `https://ai-backend-3xtk.onrender.com/healthz`가 404 → 최근 로컬 변경(멱등성 `requestId`, 긴글 청크 선검증, 회원탈퇴 `account.js`, 영어 lang 자동, 증축 가드, 회피율 고지)이 **운영에 하나도 안 올라가 있다.** 즉 지금 실사용자는 여전히 구버전 = 민원 그대로. → **"배포 + 검증"이 모든 것의 선결 조건.**
2. **가장 급한 실제 취약점은 transform 소유자 검증 부재(P0-1).** `GET /transform/:id`(transform.js:349), `cancel`(:305), `approve`(:321) 모두 토큰/소유자 검증 0 → **jobId만 알면 타인의 과제·자소서·논문 원문과 결과가 그대로 반환된다.** 데이터 유출이라 1순위.
3. **구독 보안(P0-3 cron fail-open, P0-4 webhook 무검증)은 기능 자체가 보류**지만, 엔드포인트는 살아 있다(subscription.js:211·347·359·435). → 풀 검증을 만들 게 아니라, **출시 전까지 라이브 엔드포인트를 닫는 게 가장 싸고 안전.**

## 2. Phase 0 — 배포 중지선 (목표 1~2일): 실제 취약점 차단 + 로컬 변경 라이브화

> 이게 끝나기 전에는 유료 트래픽 확대 금지(아래 §6 No-Go).

### 0-A. transform 소유자 검증 (P0-1) — 최우선 ★★★
- **무엇**: `GET /transform/:id`, `POST /transform/:id/cancel`, `POST /transform/:id/approve`에 토큰 검증 + `job.uid` 일치 검사.
- **방법**:
  - 공용 헬퍼 `requireJobOwner(req, job)`: idToken(POST는 body, GET은 `?idToken=` 또는 `Authorization: Bearer`)을 `admin.auth().verifyIdToken`으로 검증 → `decoded.uid !== job.uid`면 403, 토큰 없으면 401.
  - 프론트 폴링(`evasion-flow.js`의 `fetch('/transform/'+jobId)`)에 idToken 동봉하도록 수정(쿼리 또는 헤더). cancel/approve도 idToken body 추가.
  - devNoAuth(로컬) 경로는 기존처럼 우회 허용.
- **근거**: transform.js:305·321·349 (검증 없음 확인), 생성 시에만 검증(transform.js:259).
- **완료기준**: 타계정 토큰 GET→403, 비로그인→401, 타계정 cancel/approve→403, 본인은 정상.
- **규모**: M (백엔드 + 폴링/취소/승인 프론트 동선)

### 0-B. 구독 라이브 엔드포인트 닫기 (P0-3/P0-4, 출시 보류분) ★★★
- **무엇**: 구독 출시 전까지 외부 공격면 제거. 풀 webhook 검증은 출시 직전(Phase 3)로.
- **방법**:
  - cron fail-close: `subscription.js`의 `/subscription/charge`·`process-due`(POST/GET) 맨 앞에 `if (!process.env.CRON_SECRET) return res.status(503)` + `internalKey`/`key`가 빈값/undefined면 거부. (현재 `undefined !== undefined`=false로 통과: subscription.js:211·348·361)
  - `GET /subscription/process-due`(:359) 제거 또는 비활성(시크릿이 URL/로그에 남음).
  - `/toss/webhook`(:435): 구독 미출시이므로 **상태 변경 비활성화**(로그만 적재) 또는 라우트 자체 주석. 출시 시 서명검증+idempotency로 부활.
- **완료기준**: CRON_SECRET 미설정 시 process-due 503, 시크릿 없는 요청 403, GET 시크릿 경로 제거, 임의 webhook POST가 구독/주문 상태를 못 바꿈.
- **규모**: S

### 0-C. Firestore Rules 베이스라인 (P0-2) ★★★
- **무엇**: 저장소에 `firestore.rules` 신설(현재 전무 — `firestore.rules`/`firebase.json`/`.firebaserc` 부재 확인). 권한상승·비공개 유출 차단의 최소선.
- **베이스라인 규칙(최소)**:
  - `users/{uid}`: 본인만 read. create는 `credits==10 && plan=='free'`인 신규 문서만(나머지 필드 금지). **`credits`·`plan`·`coupon`·`subscription` 클라이언트 update 전면 금지**(서버 Admin SDK만).
  - `users/{uid}/{creditHistory,couponHistory,history,notifications}`: 본인 read, write 금지(서버만).
  - `qna`: 목록 공개 필드만 — 본문/작성자정보는 작성자·관리자(uid in ADMIN_UIDS)만 read. `answer`/`status`/`hidden`/`isFeatured` write는 관리자만.
  - `posts`/`notices`: read 공개, write 작성자·관리자. `orders`/`subscriptionOrders`/`couponCodes`/`webhookLogs`/`transformJobs`: 클라이언트 접근 금지(서버만).
- **주의**: 현재 프론트가 Firestore를 직접 쓰는 부분(Q&A 작성, 커뮤니티, 닉네임, 최초 `users/{uid}` setDoc)이 규칙과 충돌하지 않는지 동시 점검 필요 → 충돌 시 해당 동작을 서버 API로 옮기는 건 Phase 1/P2-1.
- **완료기준**: 비작성자 Q&A 본문 read = permission denied, 비관리자 answer/credits/plan update 거부, 규칙 배포 커맨드 문서화(`firebase deploy --only firestore:rules`).
- **규모**: L (규칙 작성은 M, 프론트 직접쓰기 충돌 해소가 변수)

### 0-D. probe/실험 파일 배포 격리 (P1-8 단기)
- **무엇**: 루트 `_probe-*.html`(detect/evasion/report-mock/toggle 등)·실험 로그가 배포/커밋에 안 섞이게.
- **방법**: `.gitignore`/`.vercelignore`에 `_probe-*.html`, `*.log`, 실험 md 패턴 추가. (운영 노출 시 미연결 목업이 사용자에게 보일 위험)
- **규모**: S

### 0-E. 배포 + 헬스/스모크 (P0-5) — Phase 0 마무리 ★★★
- **무엇**: 로컬 변경(§1 묶음 + 0-A~0-D)을 운영 반영 + 검증. **이게 돼야 §1의 민원 수정이 실제로 효력 발생.**
- **방법**:
  - `/healthz`에 commit SHA 노출(server.js healthz 응답에 `commit` 추가).
  - Render 백엔드 재배포 → `/healthz` 200 확인 → 스모크: `/detect-report`, `/analyze`(인증 실패 401/성공), `/transform` 생성·조회·**403(타계정)**, 결제 success/cancel 콜백.
  - 프론트 배포 원천(GitHub Pages vs Vercel) 확정 후 배포.
- **완료기준**: 운영 `/healthz` 200 + `commit/llm/firebase/uptime` 포함, 스모크 전 항목 통과, 로컬/운영 SHA 일치.
- **규모**: M

## 8. 전수조사 보고서 대비 내 계획의 차이(짚는 점)

1. **"잘 되어있는" 항목 다수가 로컬 전용 = 미배포.** healthz 404가 증거. → Phase 0에 "배포"를 명시적 게이트로 넣음(보고서엔 분산돼 있음).
2. **구독 보안(P0-3/4/P1-5)은 "풀 구현"이 아니라 "지금은 닫기".** 토스 승인 전이라 webhook 서명검증을 미리 만들 실익이 적음 → 엔드포인트 비활성이 더 싸고 안전. 풀 구현은 출시 트리거(Phase 3)로.
