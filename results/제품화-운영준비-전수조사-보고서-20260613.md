## 3. 잘 되어 있는 부분

### 3.1 크레딧 중복 차감 방지 로컬 보강

`Backend/routes/analyze.js`에 `requestId` 기반 멱등 차감이 들어가 있다.

- `commitCreditDeduct(uid, needed, opType, requestId)`
- `creditHistory` 문서 ID를 `req_${requestId}`로 고정
- 같은 작업이 재도달해도 중복 차감하지 않음
- 쿠폰 사용도 같은 방식으로 멱등 처리됨

프론트도 `genReqId()`를 발급하고, 긴 글 청크는 `requestId:chunkIndex`로 고정한다.

이건 과거 “응답 유실 후 재시도 -> 중복 차감” 민원을 구조적으로 막는 좋은 방향이다.

### 3.2 긴 글 사전 크레딧 검증 보강

`Frontend/assets/js/app-main.js`에서 5,500자 초과 입력을 청크 기준으로 미리 나누어 필요한 크레딧 합계를 계산한다.

과거 “99%에서 크레딧 부족으로 중단” 문제를 줄일 수 있다.

### 3.3 결과 실패 시 과금 방지/복구 흐름

`/analyze`와 `/analyze-pdf`는 LLM 실패 시 차감하지 않고, 차감 후 응답 전 연결이 끊긴 경우 복구 트리거를 둔다.

다만 복구 실패 시 “수동 보정 필요” 로그만 남으므로, 운영에서는 수동 보정 큐/알림이 필요하다.

### 3.4 회원탈퇴 서버 라우트 추가

`Backend/routes/account.js`가 추가되어 Firebase Admin SDK로 계정 삭제를 처리한다.

이전 카카오 재인증/비밀번호 추측 방식보다 훨씬 안전하다.

남은 과제:

- 결제/환불 기록 보관 정책과 사용자 데이터 삭제 범위를 문서화해야 함
- `orders`, `subscriptionOrders`, `posts`, `qna`, `transformJobs`, Storage 업로드 등 연관 데이터 처리 정책이 필요함

### 3.5 결제 확인 기본 구조

`/confirm-payment`는 Firebase ID Token 검증 후 Toss confirm을 호출하고, Firestore transaction으로 주문/크레딧/히스토리를 같이 처리한다.

## P0-1. `/transform/:id` 인증/소유자 검증 부재

위치:

- `Backend/routes/transform.js`
- `POST /transform/:id/cancel`
- `POST /transform/:id/approve`
- `GET /transform/:id`

현재 상태:

- 작업 생성 시에는 `idToken`으로 사용자를 검증한다.
- 그러나 이후 `jobId`만 알면 누구나 작업 상태를 조회할 수 있다.
- 완료된 작업이면 결과 본문이 그대로 반환된다.
- 승인 대기 상태면 근거 후보가 반환된다.
- 취소/승인도 소유자 검증 없이 가능하다.

리스크:

- 사용자 과제/자소서/논문 원문과 결과가 유출될 수 있음
- 타인이 작업을 취소하거나 승인할 수 있음
- `transformJobs`에 `text`, `result`, `candidates`가 저장되므로 유출 시 피해가 큼

조치:

1. `GET /transform/:id`도 `idToken` 또는 Authorization Bearer 토큰을 필수로 받는다.
2. 토큰 uid와 `job.uid`가 일치하지 않으면 403.
3. `cancel`, `approve`도 동일하게 owner check.
4. localStorage의 `lavJobRef`만 믿지 말고 서버에서 소유자 확인.
5. 운영 전 기존 `transformJobs`에 민감 데이터가 남아 있는지 정리.

Done 기준:

- 다른 계정 토큰으로 `GET /transform/{id}` 호출 시 403.
- 비로그인 호출 시 401.
- 다른 계정이 cancel/approve 호출 시 403.

## P0-2. Firestore Rules 부재와 클라이언트 직접 DB 접근

현황:

- 저장소에서 `firestore.rules`, `rules_version`, 배포용 Firebase rules 파일을 찾지 못했다.
- 프론트는 `app-module.js`에서 직접 Firestore를 읽고 쓴다.
- Q&A는 로그인 사용자가 `getDocs(collection(db,'qna'))`로 전체 문서를 읽은 뒤, 클라이언트에서 제목을 “비공개 질문입니다”로 가린다.
- 이전 Q&A 추출 보고서에서 일반 로그인 세션으로 최근 Q&A 159건을 조회했다.

리스크:

- Firestore Rules가 허술하면 비공개 Q&A 본문, 작성자 정보, 환불/계정 문의가 노출될 수 있음
- 클라이언트의 `ADMIN_ROLES`는 UI 표시용일 뿐 보안 권한이 아님
- 사용자 문서 `credits`, `plan`, `coupon`, `subscription` 같은 필드는 서버만 수정 가능해야 함
- 최초 로그인 시 프론트에서 `users/{uid}`에 `credits:10, plan:'free'`를 직접 `setDoc`한다. Rules가 정확히 제한하지 않으면 권한 상승 경로가 될 수 있음

조치:

1. Firestore Rules를 저장소에 추가하고 버전관리.
2. `users/{uid}`:
   - 본인 read 허용
   - create는 허용하더라도 `credits=10`, `plan='free'`, 허용 필드만 검증
   - `credits`, `plan`, `coupon`, `subscription`은 client update 금지
3. `qna`:
   - 목록은 공개 필드만 별도 컬렉션/서버 API로 제공
   - 본문은 작성자/관리자만 read
   - 답변/상태 수정은 관리자만
4. `posts`, `notices`, `orders`, `subscriptionOrders`, `creditHistory`, `couponHistory` 각각 read/write 정책 명시.
5. 관리자 기능은 가능한 백엔드 Admin SDK API로 이동.

Done 기준:

- 비작성자가 Q&A 본문 doc read 시 Firestore permission denied.
- 비관리자가 `answer`, `status`, `hidden`, `isFeatured`, `credits`, `plan` 업데이트 시 거부.
- Rules 배포 커맨드와 테스트가 문서화됨.

## P0-3. 정기결제 cron 인증 fail-open 가능성

위치:

- `Backend/routes/subscription.js`
- `/subscription/charge`
- `/subscription/process-due`

문제:

```js
if (internalKey !== process.env.CRON_SECRET) return res.status(403)
```

`CRON_SECRET`이 미설정이고 요청에도 `internalKey`가 없으면 `undefined !== undefined`가 false가 되어 통과할 수 있다.

같은 패턴이 `GET /subscription/process-due?key=...`에도 있다.

리스크:

- 환경변수 실수 하나로 정기결제 갱신 엔드포인트가 외부에 열릴 수 있음
- GET 쿼리 방식은 secret이 URL, 로그, 브라우저 히스토리, 프록시 로그에 남을 수 있음

조치:

1. 모든 내부 엔드포인트에서 먼저 `if (!process.env.CRON_SECRET) return 503`.
2. 요청 secret도 빈 문자열/undefined/null 거부.
3. GET 인증 방식 제거 또는 임시 유지 시 즉시 deprecated.
4. `Authorization: Bearer ${CRON_SECRET}` 헤더 방식으로 통일.
5. Render Cron에서 POST/헤더 호출로 전환.

Done 기준:

- `CRON_SECRET` 미설정 환경에서 `/subscription/process-due`는 무조건 503.
- secret 없는 요청은 403.
- GET query secret 방식 제거.

## P0-5. 운영 배포본과 로컬 코드 불일치

확인 결과:

- 로컬 `Backend/server.js`에는 `/healthz`, `/api/health`가 있다.

- `https://gpkorea.ai.kr/`는 200을 반환했지만 헤더상 GitHub Pages/Fastly/Cloudflare 경로로 보인다.

해석:

- 로컬 최신 코드가 Render에 아직 배포되지 않았거나, 운영 서비스가 다른 코드/브랜치를 보고 있을 가능성이 있다.
- 제품화 판단은 로컬 코드만으로 끝나면 안 되고 운영 배포본 검증이 필요하다.

조치:

1. 운영 백엔드 commit SHA를 `/healthz`에 노출.
2. 프론트에도 `APP_VERSION` 또는 배포 SHA를 footer/debug에 노출.
3. Render/Vercel/GitHub Pages 중 실제 운영 배포 원천을 하나로 정리.
4. 배포 후 smoke test:
   - `/healthz`
   - `/detect-report`
   - `/analyze` 인증 실패/성공
   - `/transform` 생성/조회/403
   - 결제 success/cancel callback

Done 기준:

- 운영 URL에서 `/healthz` 200.
- 응답에 `commit`, `llm`, `firebase`, `uptime`, `transformStats` 포함.
- 로컬/운영 버전 불일치 시 배포 차단.

- CORS는 `gpkorea.ai.kr` 중심이라 Vercel preview에서는 API 요청이 막히거나, 막으려고 CORS를 넓히면 운영 API가 preview에 노출됨

조치:

1. `APP_ENV=production|staging|preview|local` 분리.
2. preview는 별도 Firebase project 또는 읽기 전용 mock API 사용.
3. preview는 Toss test key만 사용.
4. `SITE_URL`은 `window.location.origin` 기반으로 분기.
5. Vercel 환경변수로 `API_BASE`, `TOSS_CLIENT_KEY`, `FIREBASE_CONFIG` 분리.

Done 기준:

- Vercel preview에서 live Toss key가 절대 로드되지 않음.
- preview에서 운영 Firestore에 쓰기 불가.
- preview에서 운영 크레딧/결제 API 호출 불가.

## P1-1. 개인정보 문구와 실제 저장 동작 불일치

프론트 본문에는 “입력한 데이터는 자동 저장 없이 검사 후 즉시 삭제” 취지 문구가 있다.

하지만 실제로는 다음 저장 경로가 있다.

- `transformJobs`에 `text`, `result`, `candidates` 저장
- 사용자 히스토리 저장
- `evasion-flow.js` localStorage 보관함에 결과 저장
- Q&A/커뮤니티에 사용자가 입력한 본문 저장

리스크:

- 개인정보처리방침/서비스 설명과 실제 데이터 처리 방식이 불일치

조치:

1. “자동 저장 없이 즉시 삭제” 문구를 실제 정책에 맞게 수정.
2. 히스토리 저장 on/off 옵션 제공.
3. `transformJobs`의 `text`는 승인 단계에 필요한 최소 시간만 보관하고 TTL 정리.
4. 저장 기간을 UI/정책에 명시.
5. 탈퇴 시 삭제/익명화/법정 보관 데이터를 구분.

## P1-3. 무료 AI 감지 원가와 abuse 방어

`/detect-report`는 무료이며 LLM 판정 + 1문장 미리보기를 실행한다.

현재 한도:

- 메모리 `Map`
- 로그인 uid 또는 IP 기준
- 기본 하루 5회
- 서버 재시작 시 초기화
- 다중 인스턴스에서 공유 안 됨

리스크:

- 무료 기능이 비용 공격 지점이 될 수 있음
- Render 재시작/스케일아웃 시 일일 한도 우회 가능
- 비로그인 IP 기준은 학교/기숙사/공유망에서 오차단 가능

조치:

1. 일일 무료 사용량을 Firestore/Redis/KV에 저장.
2. 비로그인은 짧은 글/낮은 max token으로 제한.
3. 로그인 전환 유도: 비로그인 1~2회, 로그인 5회.
4. 비용 지표 기록:
   - detect calls
   - llm fallback ratio
   - preview generation cost
   - conversion rate to paid

## P1-8. 빌드/배포 체계 부족

프론트는 정적 HTML/JS/CSS라 단순 배포는 쉽다. 하지만 운영 제품화 관점에서는 아래 문제가 있다.

- `page-loader.js`가 synchronous XHR로 partial을 로드함
- JS/CSS 파일이 크고 분할/압축/해시 전략이 없음
- 캐시가 `max-age=0, must-revalidate`라 매번 재검증
- 디자인 probe 파일이 루트에 있음
- Vercel 설정은 있으나 현재 `gpkorea.ai.kr`은 GitHub Pages 계열로 보임
- 테스트/린트/빌드 스크립트 없음

조치:

1. 단기:
   - `_probe-*.html` 제거 또는 `.vercelignore`/배포 제외
   - `version` 상수로 캐시 무효화 통일
   - partial sync XHR 제거 또는 초기 HTML에 포함
2. 중기:
   - Vite 기반 정적 빌드로 이전
   - JS/CSS 번들 분리/해시/압축
   - Preview/Staging/Production 환경 분리
3. 장기:
   - React/Next는 지금 당장 필수는 아니지만, 페이지/상태/컴포넌트가 더 커지면 도입 검토

### P2-5. 장기 실행 작업 아키텍처

현재 `/transform`은 Express 프로세스 내부 memory map + Firestore 영속화 조합이다.

장점:

- 구현이 단순함
- 단일 Render 인스턴스에서는 동작 가능

한계:

- 다중 인스턴스/스케일아웃에 부적합
- memory daily cap은 재시작/스케일아웃 시 공유 안 됨
- 서버 재시작 시 running job은 중단 처리
- job 취소/승인/조회 소유자 보안이 아직 없음

중기 권장:

- Cloud Tasks / BullMQ / Redis Queue / Render worker 분리
- job 상태는 DB 단일 진실 원천
- 동시성/일일한도는 Redis/Firestore transaction으로 관리
- LLM 호출 비용/토큰을 job별 기록

## 7. 배포 전략 제안

### 7.1 현 상황

- 백엔드: Render 운영 주소 사용 중으로 보임
- 프론트: `gpkorea.ai.kr`은 GitHub Pages 계열 헤더가 확인됨
- 프론트 저장소에는 Vercel 설정이 있음
- 디자인 시안/프론트 작업을 Vercel preview에 올리고 싶다는 요구가 있었음

### 7.2 추천 구조

단기 운영:

- Production frontend: 기존 운영 도메인 유지
- Preview frontend: Vercel preview 별도 프로젝트
- Backend production: Render 유지
- Backend staging: Render 별도 서비스 또는 same backend with staging Firebase

단기 원칙:

- preview는 운영 DB/운영 Toss live key를 쓰지 않는다.
- production 백엔드 CORS에는 production origin만 둔다.
- preview 백엔드 CORS는 preview origin만 둔다.

중기:

- 프론트는 Vercel로 이전 가능.
- 백엔드는 Render 유지 가능하나 long-running LLM 작업은 worker/queue 분리 전까지 단일 paid instance 운영이 현실적.
- Next/Vercel Serverless로 `/transform` 같은 5~90분 작업을 옮기는 것은 부적합.

### 7.3 Vercel 이전 시 체크

필수:

- `VITE_API_BASE` 또는 정적 config 생성
- `VITE_SITE_URL`
- `TOSS_CLIENT_KEY` env 분리
- Firebase config env 분리
- `.vercelignore`에 `_probe-*`, 로그, 실험 결과 제외
- preview 배포 보호 또는 Basic Auth

## 14. 종합 의견

이 프로젝트의 가장 큰 문제는 “기능이 없어서”가 아니라, **기능이 빠르게 붙으면서 운영 경계가 아직 정리되지 않은 것**이다.

엔진/UX/디자인 실험은 이미 많이 진행됐다. 크레딧 멱등성, 긴 글 사전검증, 무료 감지 분리, 서버 탈퇴 라우트 같은 최근 개선도 방향이 좋다.

하지만 제품화는 기능 완성보다 **신뢰 손실 방지**가 먼저다. 지금 사용자 불만은 대부분 아래 네 가지로 모인다.

1. 돈이 빠졌는데 결과를 못 받았다.
2. 결과를 받았는데 외부 검사기 수치가 그대로다.
3. 환불 기준이 예상과 다르다.
4. 문의했는데 처리가 느리거나 기준이 불명확하다.

따라서 운영 전 핵심은 다음이다.

- 보안상 타인의 데이터가 절대 보이지 않게 막기
- 결제/크레딧/환불의 원장을 정확히 남기기
- 장애 시 자동 복구가 안 되면 운영자가 즉시 알게 하기
- 외부 검사기 결과에 대한 기대치를 결제 전에 조정하기
- preview와 production을 완전히 분리하기

P0를 막은 뒤에야 Vercel 프론트 이전, 디자인 시안 선택, React/Next 도입 여부 같은 프론트 구조 논의가 의미 있다.
