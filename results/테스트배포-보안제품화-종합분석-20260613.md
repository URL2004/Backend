## 1. 결론

테스트 배포 구조 자체는 올바른 방향이다.

- 운영 프론트 `main`과 별도로 `deploy/staging-vite` 브랜치를 만들었다.
- 운영 Render backend와 별도로 `ai-backend-staging` 서비스를 만들었다.
- Vercel preview frontend는 staging Render backend를 바라본다.
- Backend staging에는 `transform` 소유자 검증, cron fail-close, webhook fail-close, `/analyze-pdf` 410, Firestore rules 테스트가 들어갔다.

하지만 현재 상태로는 아직 “안전한 staging 테스트 환경”이라고 보기 어렵다.

가장 큰 이유는 아래 5개다.

1. Vercel preview frontend가 아직 운영 Firebase config로 fallback된다.
2. Render staging 서비스가 Render의 `Production` environment 안에 같이 들어가 있다.
3. 운영 Render cron은 아직 query string secret 방식이고, CLI/로그에 secret이 노출될 수 있다.
4. Vercel preview protection bypass secret을 발급해 테스트 URL로 쓰고 있어, 테스트 종료 후 반드시 revoke/rotate가 필요하다.
5. 새 Firestore rules와 현재 프론트의 직접 Firestore 접근 방식이 일부 충돌한다. 특히 일반 사용자 Q&A 목록 조회가 깨질 가능성이 높다.

따라서 다음 단계는 “디자인 확인”보다 먼저 **staging 데이터/인증/결제 분리**와 **운영 secret 회전**이다.

만 담당한다.

이 방식은 Next/React로 한 번에 갈아엎는 것보다 지금 단계에서는 안전하다.

### 4.3 Backend staging에서 P0 일부가 닫혔다

확인된 개선:

- `/transform/:id` 조회/승인/취소 owner check 추가

## P0-2. 운영 Render cron secret이 query string에 남아 있다

위치:

- Render cron `subscription-process-due`
- 현재 운영 cron command가 `/subscription/process-due?key=...` 형태

현재 상태:

- staging 코드에서는 GET `/subscription/process-due`가 410으로 닫혔다.
- 하지만 운영 cron은 아직 query string secret 방식이다.
- Render CLI 출력에서도 cron command 안에 secret이 노출될 수 있다.

리스크:

- URL, CLI 출력, 로그, shell history, Render dashboard에 secret이 남음
- secret이 노출되면 정기결제 cron을 외부에서 호출할 수 있음
- staging 브랜치를 production에 반영하면 기존 cron은 410으로 실패한다.

조치:

1. 운영 `CRON_SECRET` 즉시 회전.
2. Render cron command를 POST + `Authorization: Bearer` 방식으로 변경.
3. 운영 backend에 staging의 cron fail-close 패치를 배포하기 전 cron job을 먼저 교체.
4. 과거 로그/스크린샷/문서에 secret이 남아 있으면 폐기.

예시:

```bash
curl -fsS -X POST https://ai-backend-3xtk.onrender.com/subscription/process-due \
  -H "Authorization: Bearer $CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d "{}"
```

## P0-4. Render staging이 `Production` environment 안에 있다

현재 상태:

- 운영 `ai-backend`와 staging `ai-backend-staging`이 같은 Render project/environment에 들어 있다.

리스크:

- 운영 env group이나 secret을 실수로 staging에 붙일 수 있음

조치:

1. Render에 `Staging` environment를 별도로 만든다.
2. `ai-backend-staging`을 staging environment로 옮기거나 새로 생성한다.
3. service name, env, dashboard label에 `staging`을 명확히 표시한다.
4. staging secret은 `test_` Toss, staging Firebase, 별도 Anthropic key만 사용한다.

- event idempotency 저장이 없다.

조치:

1. Toss 공식 webhook 인증 방식 확인 후 구현.
2. 불가피하게 custom secret을 쓴다면 Toss webhook 앞단 proxy 또는 Toss 콘솔에서 header 전달 가능 여부 확인.
3. `webhookEvents/{eventId}` 저장으로 중복 이벤트 방지.
4. 상태 변경 전 Toss API로 `paymentKey/orderId` 재조회.

### P1-4. 결제 secret 미설정 시 명확히 fail-close해야 한다

위치:

- `routes/payment.js`
- `routes/subscription.js`

현재:

- subscription 쪽 `tossBasicToken()`은 `TOSS_SECRET_KEY_MISSING`을 throw.
- payment confirm/refund 쪽은 `process.env.TOSS_SECRET_KEY`가 없으면 `undefined:`로 Basic token을 만들 가능성이 있다.

리스크:

- staging에서 결제 API를 누르면 외부 Toss API에 잘못된 인증으로 나감
- 사용자에게 원인 불명 500/401이 보일 수 있음

조치:

1. payment route에도 `requireTossSecret()` 추가.
2. secret 미설정 시 503 + 명확한 메시지.
3. production 시작 시 필수 env validation 추가.

### P1-5. 사용자 원문 저장 정책과 문구 정합이 필요하다

확인된 저장 경로:

- `users/{uid}/history`에 `inputText`, `outputText` 저장
- `transformJobs`에 `text`, `result`, `candidates` 저장
- localStorage에 `lavJobRef` 저장
- Q&A/커뮤니티 본문 Firestore 저장

리스크:

- “검사 후 즉시 삭제”류 문구와 실제 저장 동작이 다를 수 있음
- 과제/자소서/논문 원문은 민감 데이터로 취급해야 함
- 탈퇴 시 어느 데이터가 삭제되는지 명확하지 않음

조치:

1. 히스토리 저장 on/off 옵션.
2. transform job 원문 TTL 삭제.
3. 개인정보 처리방침에 실제 저장 항목/기간 명시.
4. 탈퇴 시 `history`, `transformJobs`, Q&A, posts, storage 첨부파일 처리 범위 정의.

### P1-6. Render free staging은 긴 job 검증에 부적합하다

현재 staging plan:

```txt
free
```

리스크:

- 스핀다운/콜드스타트
- 긴 transform job 테스트 중 중단 가능
- 운영과 성능 특성이 다름

권장:

- 단순 헬스/보안 smoke는 free 가능
- 실제 5~90분 transform job, 결제/웹훅, 동시성 테스트는 starter 이상으로 올려 테스트

## 7. P2: 운영 품질/구조 개선

### P2-1. 현재 Vite 이식은 “빌드 파이프라인 도입” 단계다

현재 방식:

- Vite가 실제 앱 JS를 번들링하지 않음
- 레거시 `index.html`과 `/assets/js/*.js`를 그대로 복사
- `runtime-config.js`만 생성

장점:

- 기존 앱을 깨뜨릴 위험이 낮음
- Vercel 배포 산출물과 env 분리가 가능

한계:

- JS/CSS tree-shaking 없음
- 전역 함수/전역 상태 유지
- CSP 적용이 어렵다
- 파일별 캐시 무효화가 수동 query string에 의존

권장:

1. 지금은 이 구조로 staging 검증.
2. 다음 단계에서 Vite entry를 점진적으로 도입.
3. 이후 React/Next 도입 여부 결정.

### P2-2. CSP/보안 헤더가 부족하다

현재:

- `vercel.json`에는 cache headers만 있음
- CSP, X-Frame-Options, Referrer-Policy, Permissions-Policy 없음

권장:

- staging에서 먼저 CSP report-only 적용
- inline script가 많아 바로 강제 CSP는 어려움
- 최소 헤더:
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
  - `Frame-Options` 또는 `frame-ancestors`

### P2-3. 관리자 권한은 UID hardcode보다 custom claims가 낫다

현재:

- `config.js`
- `firestore.rules`
- frontend `isAdmin()`

에 관리자 UID가 하드코딩되어 있다.

리스크:

- UID 추가/삭제 시 코드와 rules를 모두 배포해야 함
- 프론트 `isAdmin()`은 UI 표시일 뿐 보안 기준이 아님

권장:

- Firebase custom claims `admin:true`
- Firestore rules도 `request.auth.token.admin == true`
- 서버 API도 custom claim 또는 서버 env allowlist로 검증

### P2-4. API rate limit이 메모리 기반이다

현재:

- Express rate limit
- transform daily cap도 메모리 기반

리스크:

- 서버 재시작 시 초기화
- 다중 인스턴스에서 공유 안 됨
- 무료 감지 비용 방어가 약함

권장:

- Redis/Upstash/Firestore counter
- uid + IP + device fingerprint 조합
- detect-report 무료 기능은 비용 지표와 함께 대시보드화

### P2-5. 관측성/수동 보정 큐가 필요하다

현재:

- `console.log` 중심
- 수동 보정 필요 로그는 있지만 별도 큐/알림 없음

필요:

- `manualCorrections` 컬렉션
- Slack/Discord/Email 알림
- 결제 성공/실패, 환불 요청, 차감 실패, LLM 실패, webhook 실패 대시보드
- requestId/jobId를 사용자 문의 화면에 표시
